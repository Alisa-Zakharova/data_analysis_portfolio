# A/B тест формы оплаты: анализ с кластерным бутстрепом

Учебный кейс: как правильно считать результаты A/B-теста, когда у одного
пользователя несколько попыток. Показываю, почему обычный z-тест по строкам
даёт завышенную значимость, и как это обойти.

## Задача

Проверить, повышает ли новая форма оплаты конверсию из шага 1 (открыл форму)
в шаг 4 (успешная оплата). Рандомизация по пользователям, две группы A/B,
30 дней.

## Данные

Два листа: ~1500 пользователей (группа, возраст, город, устройство) и
~2660 попыток оплаты с шагами воронки. Одна строка в платежах - это попытка,
а не человек. У одного пользователя может быть несколько попыток.

## Результат

| Метрика | A | B | Эффект |
|---|---|---|---|
| Конверсия 1→4 по попыткам (ключевая) | 49,8% | 64,4% | +14,6 п.п., 95% ДИ [11,0; 18,3] |
| Доля пользователей с успешной оплатой | 65,6% | 80,4% | +14,7 п.п., z-тест p ≈ 1e-10 |
| Успешных оплат на пользователя | 0,87 | 1,16 | Mann–Whitney p < 1e-11 |

Эффект положительный во всех сегментах и во все четыре недели теста.
Ноль не входит в 95% интервал - разница вряд ли случайна.

## Логика расчета 
Главная проблема - **кластеризация**: попытки одного пользователя похожи
между собой. Если считать их независимыми, ошибка занижается, а p-value
получается слишком маленьким.

Поэтому:

- **Ключевая метрика (ratio, clustered):** точечная оценка по попыткам,
  95% интервал - кластерный бутстреп по пользователям, p-value -
  перестановочный тест по пользователям.
- **Пользовательская метрика:** одна строка на человека, обычный z-тест.
- **Счётчики (оплаты на человека):** Mann–Whitney, распределение скошенное.

## Проверки перед выводами

- SRM в порядке: 752 / 751 пользователей, p ≈ 0,98.
- По городу и возрасту группы похожи.
- По устройству небольшой перекос (p ≈ 0,05), но эффект одинаков на
  Android и iOS - на вывод не влияет.
- Чистка данных: убрал пользователя без группы, платёж без `user_id`,
  платёж с конфликтом группы. Возраст вне 14–90 заменил на NaN.

## Рекомендация

Раскатывать новую форму на всех, но поэтапно (50% → 100%) и с мониторингом.
Перед полной раскаткой:

1. Уточнить у разработки, что в B менялось только форма - конверсия выросла
   и на шагах, где автозаполнение не должно влиять.
2. Добавить защитные метрики: ошибки оплат, возвраты, обращения в поддержку.
3. Оставить 5% пользователей на старой версии после раскатки - контроль на
   длинной дистанции.
