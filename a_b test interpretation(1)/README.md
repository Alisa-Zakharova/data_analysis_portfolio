# Cluster-robust A/B analysis

Учебный кейс: анализ A/B-теста с рандомизацией по пользователям. Показывает,
почему стандартный z-тест по строкам даёт завышенную значимость для
ratio-метрик с кластеризованными наблюдениями, и как корректно считать
инференс через кластерный бутстреп и перестановочный тест.

## Бизнес-вопрос

Увеличивает ли новая версия формы долю успешных завершений воронки?

- **Гипотеза:** новая форма с автозаполнением полей повышает конверсию.
- **Ключевая метрика:** конверсия из шага 1 (открыл форму) в шаг 4
  (успешное завершение), **по попыткам**.
- **Дизайн:** 30 дней, рандомизация по пользователям, две группы A/B.

## Данные

| | Пользователи | Попытки |
|---|---|---|
| Строк (до очистки) | ~1 500 | ~2 660 |
| Полей | `user_id`, `group`, `age`, `city`, `device_type` | `payment_id`, `user_id`, `group`, `step1..step4` (timestamps) |

Ключевая особенность: **одна строка в таблице попыток - это одна попытка,
а не один человек**. У одного пользователя может быть несколько попыток,
поэтому наблюдения внутри пользователя не независимы (clustering).

Данные синтетические / обезличенные (id вида 1001–2500, 5001–7657,
искусственные аномалии 9001–9004, 99001–99003), публикация не нарушает
конфиденциальности.

## Результат

| Метрика | A | B | Эффект |
|---|---|---|---|
| Конверсия 1→4 по попыткам (ключевая) | ≈ 50% | ≈ 64% | **+14,6 п.п.**, 95% CI [11,0; 18,3], permutation p < 1e-4 |
| Доля пользователей хотя бы с одной успешной оплатой | ≈ 66% | ≈ 80% | +14,7 п.п., z-тест p ≈ 1e-10 |
| Успешных оплат на пользователя | ≈ 0,87 | ≈ 1,16 | Mann–Whitney p < 1e-11 |
| Попыток на плательщика | 1,74 | 1,80 | различия нет (MW p ≈ 0,15) |

Эффект положительный во всех сегментах (Android +14,9 п.п., iOS +14,1,
Москва +18,3, СПб +14,2, регионы +10,7) и во все четыре недели теста
(+15,3 / +13,6 / +14,3 / +14,6 п.п.) - эффекта новизны нет.

## Как считали (методология)

Ключевая сложность - **кластеризация**: у одного пользователя несколько
попыток, они коррелируют между собой. Наивный z-тест по строкам считает
их независимыми, занижает стандартную ошибку и даёт завышенный p-value
(pseudoreplication).

Что сделано:

1. **Ключевая метрика (ratio, clustered):**
   - точечная оценка - по попыткам: `Σ success / Σ attempts`;
   - 95% CI - **кластерный бутстреп** (резэмплирование пользователей
     со всеми их попытками);
   - p-value - **кластерный перестановочный тест** (10 000 перестановок
     метки группы на уровне пользователя).

2. **Пользовательская метрика (бинарная, независимая):**
   - агрегация до одного пользователя = одна строка;
   - **z-тест для двух долей** (n достаточно велико: `n·p ≥ 5`).

3. **Счётчики (успешных оплат на пользователя):**
   - **Mann–Whitney U** - распределение скошенное, много нулей,
     t-тест некорректен.

4. **Сегменты:** те же методы, но без агрессивных выводов о
   различиях между сегментами - интервалы пересекаются, а
   множественные сравнения повышают шанс ложных находок.

### Чек-лист корректности

- [x] SRM проверен: 752 / 751 пользователей, χ² p ≈ 0,98.
- [x] Баланс по городу и возрасту: различий нет.
- [x] Перекос по устройству (p ≈ 0,053) отработан отдельно:
      эффект одинаков на Android и iOS, на вывод не влияет.
- [x] Данные очищены: удалён пользователь без группы, платёж без
      `user_id`, платёж с конфликтом группы. Возраст вне 14–90
      заменён на NaN, пользователи сохранены.
- [x] Пользовательская метрика пересчитана по всем
      рандомизированным пользователям (включая «молчунов» с 0 попыток);
      результат совпадает с расчётом «по плательщикам» до 0,2 п.п.

## Рекомендация

Раскатывать новую форму на всех пользователей поэтапно (50% → 100%)
с мониторингом защитных метрик, которых в тесте не было.

Перед полной раскаткой:

1. Согласовать с командой разработки, какие изменения были в B - конверсия
   выросла и на шагах, где автозаполнение полей не должно влиять, время
   на шагах не изменилось. Возможно, в B попало что-то ещё.
2. Добавить защитные метрики: ошибки и отказы платежей, возвраты и отмены,
   обращения в поддержку, доля ручных правок автозаполненных полей.
3. Оставить 5% пользователей на старой версии после полной раскатки -
   контроль на длинной дистанции.

## Что остаётся неясным

1. **Механизм эффекта.** Автозаполнение должно помогать на переходе
   1→2, но конверсия выросла и на 2→3, и на 3→4. Нужно подтверждение
   от разработки, что менялась только форма полей.
2. **Риски для качества платежей.** Данных об ошибках, возвратах,
   обращениях в поддержку нет. Возможен рост доли ошибочных платежей
   при росте конверсии.
3. **Один месяц данных.** Сезонность (например, пик платежей в конце
   месяца) не проверена.
